Test case analysis for character loss issue:

Original issue in code block:
Text: "export OPENSSL_DIR"
When wrapped, 'S' is missing from 'OPENSSL'

New issue in markdown text:
Text: "arise" -> 'a' is missing
Text: "from" -> 'f' is missing

Key observations:
1. The wrap_text_with_estimates function seems to be setting wrap_pos correctly
2. When wrapping at a space (line 1566), wrap_pos is set to space_pos (the position of the space)
3. The WrappedLine byte_end is set to line_byte_start + wrap_pos (line 1587)
4. For the next line, if we wrapped at a space, current_pos = wrap_pos + 1 (line 1601)

Potential issue #1: 
When wrapping at space_pos, the wrapped line ends AT the space, not BEFORE it.
So if we have "OPENSSL DIR" and wrap at the space between them:
- wrap_pos = position of space
- First line ends at the space (includes "OPENSSL ")
- Next line starts at wrap_pos + 1 (skips the space)

But if the space is being included in the line AND we're skipping leading spaces, 
we might be double-skipping?

Potential issue #2:
In shape_line_with_styles (line 1636), we extract:
let full_line_text = &original_text[line.byte_offset..line.byte_end];

Then if skip_leading_spaces is true (line 1639):
let line_text = &full_line_text[line.leading_space_bytes..]

This could be dropping a character if leading_space_bytes is calculated wrong.

Potential issue #3:
The wrap_pos in wrap_text_with_estimates might be off by one when wrapping at a space.
When we find a space at position N, we set wrap_pos = N.
But this means the wrapped line includes the space.
When we start the next line at wrap_pos + 1, we're starting AFTER the space.

If the next character after the space is what's being lost, this could be the issue.
